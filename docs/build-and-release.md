# Сборка и выпуск

## Локальный комплект

`VERSION`, `PackageVersion` в `.iss` и метаданные native EXE должны соответствовать текущей версии. Сейчас это 1.1.0; Windows file version — 1.1.0.0. Git-тег стабильного релиза имеет вид `v1.1.0`.

Сначала соберите и проверьте агент, затем установщик. Compiler directory для `build-agent.ps1` должен содержать x64 MinGW-w64 и `windres`. Закреплён w64devkit 2.9.1; загрузчик инструментов читает SFX как архив и проверяет SHA-256. Эти инструменты не входят в клиентский runtime.

Чистый исходный пакет QIP хранится только в `private/payload`. Контрольная сумма исходного 7z: `0bcc0f2b0914f89af68200fd811e8c96b9f28fcbdac8ff034bdf02a81fd13a0c`. Скрипт проверяет 151 исходный файл и точный набор каталогов. Копирование своего рабочего `Users` в этот пакет запрещено.

`build-installer.ps1` проверяет подпись официального ISCC, статически извлекает оригинальную иконку, компилирует `.iss`, создаёт манифест и проверяет его подпись и SHA-256. В готовую программу входят только клиент, собственные нативные компоненты, метаданные версии и уведомления о лицензиях. Python и компилятор не устанавливаются пользователю.

Для проверки перехода между версиями:

```powershell
.\scripts\test-installer.ps1 -ISCC C:\tools\Inno\ISCC.exe -BaselineSourceDirectory C:\private\source-1.0.0 -WorkDirectory C:\private\isolated-test
```

Тест компилирует отдельный общий AppId и отдельные имена всех ярлыков. Он не должен менять действующую установку. Приватный параметр `-RealBaseline` позволяет проверить копию реальных профилей. Эта копия и полный тестовый каталог остаются вне Git; в отчёт попадают только результаты и количество файлов.

## Ключ подписи

Публичный ключ — `updater/keys/release-public.pem`; приложение содержит тот же RSA-модуль. Локально созданный приватный ключ защищён DPAPI исходной учётной записи Windows. Его шифрованный файл находится в рабочем приватном каталоге этой задачи, вне репозитория. Сохраните его и независимую защищённую резервную копию прежде, чем публиковать приложение с этим доверенным ключом. DPAPI-файл не является переносимым секретом для другого компьютера или пользователя.

Для CI нужен environment secret `MANIFEST_SIGNING_KEY_B64`. Его можно отправить из исходной учётной записи после явного решения владельца:

```powershell
python scripts/configure-signing-secret.py --key-dpapi C:\private\release-signing-key.dpapi --environment qip-release
```

Эта команда действительно меняет секрет GitHub и требует авторизованного `gh`; при подготовке текущего проекта она не запускалась. Приватное значение передаётся в stdin, без аргументов и временного открытого файла. Публичный ключ при подписании должен совпасть. Утеря секрета потребует отдельной процедуры смены доверенного ключа или ручной установки.

## GitHub Actions

- `ci.yml`: Windows runner, проверка исходников, сборка нативного агента и тесты на PR и push. Только `contents: read`, без секретов и загрузки бинарных artifacts.
- `private-build.yml`: ручной запуск на собственном runner с метками `self-hosted, Windows, X64, qip-private`. Использует локально полученный пакет и environment `qip-private-build`; дистрибутив остаётся на runner.
- `release.yml`: ручной запуск с `approval=PUBLISH_STABLE` из `main`. Сначала тесты. Затем environment `qip-release` с обязательными required reviewers, сборка подписанного установщика, проверка и публикация. Перед работой с исходным пакетом необходимо письменное подтверждение прав в `docs/redistribution.json` и соответствующий документ.

Для приватного runner задайте variables `QIP_TOOLCHAIN`, `QIP_ISCC`, `QIP_PRIVATE_PAYLOAD`. Установите Python и `requirements-ci.txt`. Секрет подписи хранится в environment.

Для публичного выпуска, когда разрешение подтверждено, задайте HTTPS secret `QIP_SOURCE_PACKAGE_URL`, возвращающий именно исходный архив с закреплённым SHA-256, и `MANIFEST_SIGNING_KEY_B64`. Не помещайте приватный пакет в публичный artifact workflow. Защитите `main` проверками CI и review. Без настроенных reviewers release workflow остановится; без прав распространения он также остановится.

Выпускаются установщик, `SHA256SUMS.txt`, `update-manifest.json`, `update-manifest.sig` и описание из `docs/RELEASE_NOTES.md`. Право `contents: write` выдаётся только job публикации, `actions: read` используется для проверки environment. GitHub-токен не попадает в приложение. Публикация сначала создаёт draft и затем стабильный Release после всех ворот текущего job.

Исходники опубликованы в `main` после отдельного подтверждения владельца. [Проверка исходников, сборка агента и тесты на GitHub Windows runner](https://github.com/kappapr1der/qip2005-jimm/actions/runs/38450953722) завершились успешно. Тест с приватными реальными профилями выполнялся только локально; эти данные на runner не передавались. Приватный build и публичный release workflows не запускались, environments и signing secrets не настроены этим агентом. Права распространения остаются неподтверждёнными, полного дистрибутива на GitHub нет.
